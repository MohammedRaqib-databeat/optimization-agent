Google Ad Manager Onboarding Automation

How to deploy the pure-Apex GAM authentication wizard to a new Salesforce org, so any client admin can connect their own GAM account with no CLI, no JVM, and no external services.

1
Context

How the automation works

Three problems stood between "client has a GAM JSON key" and "Salesforce can call the GAM API," and each one is solved by a different piece of this package.

Client pastes JSON → Apex builds .jks file → Client imports it (Setup) → Apex deploys metadata → Apex detects GAM network → Connected
Problem 1 — Salesforce only accepts real JKS filessolved by GAMJKSBuilder.cls

Setup's "Import from Keystore" screen rejects everything except genuine Java KeyStore format — no API exists to upload one directly. GAMJKSBuilder.cls builds a real JKS binary entirely in Apex: it parses the client's pasted key, constructs and self-signs an X.509 certificate from scratch, encrypts the key with Java's proprietary keystore cipher, and assembles the container — validated byte-for-byte against real keytool output during development.

Problem 2 — No API creates External/Named Credentialssolved by GAMOnboardingProvisioningService.cls

Once the client imports the certificate, someone still has to create the External Credential, Named Credential, and Permission Set that actually use it. Neither is Tooling-API-insertable, so this class builds their metadata XML in Apex, packages it into a real ZIP (via a hand-built ZIP writer, since Apex has no compression API), and deploys it through a raw SOAP call to the org's own Metadata API — using the running admin's own session, no stored credentials anywhere.

Problem 3 — The client doesn't know their own GAM network codesolved by GAMNetworkServiceClient.discoverNetwork()

GAM's API normally requires a network code just to make a call — a chicken-and-egg problem for a brand-new connection. getAllNetworks() is the one GAM operation that works without a network code supplied, so it's used once, immediately after the credential is live, to detect and store the real code automatically.

4
Client-facing · no CLI needed

Generate the keystore

This is the part the client actually does. No terminal, no JVM, no manual conversion.

Steps

1. Open the GAM Onboarding Wizard page.

2. Paste the full contents of the GAM service account JSON file into the text box.

3. Click Convert and Continue.

4. The browser automatically downloads a .jks file, and a keystore password is shown on screen with a copy button.

Behind the scenes: GAMJKSBuilder.cls extracts the private key, builds and self-signs a certificate, encrypts the key, and assembles the keystore — all in a single Apex transaction, nothing written to any object or log.

5
The one unavoidable manual step

Import into Setup

Salesforce provides no API for this — confirmed by direct testing against the Metadata and Tooling APIs. It is a single click.

Steps

1. The wizard's result screen links directly to Setup → Certificate and Key Management.

2. Click Import from Keystore.

3. Select the downloaded .jks file and paste in the password from the previous step.

4. Click Import. You should see a new certificate named gam_service_account_key, Self-Signed, with Exportable Private Key checked.

5. Return to the wizard and click I've Imported It — Continue.

6
Fully automatic from here

Auto-provisioning finishes the connection

Clicking Continue runs four Apex calls in sequence. The wizard shows a spinner with live status text through all of them.

What happens, in order
StepApex methodWhat it does
1startProvisioning()Builds and deploys the External Credential, Named Credential, and Permission Set metadata via the Metadata API
2checkStatus()Polled every 3 seconds until the deploy reports Succeeded or Failed
3assignPermissionSet()Grants the running admin access to the new External Credential principal
4discoverNetwork()Calls GAM's getAllNetworks(), stores the detected network code in GAM_Config__c

These run as four separate Apex round trips, not one transaction — Salesforce disallows a callout in the same transaction as a preceding DML statement, and steps 3 and 4 are exactly that combination.

Success screen

The wizard ends on a confirmation screen showing the detected GAM network name and code. At that point the connection is fully live and usable by any Apex code that calls the GAM_API Named Credential.

Confirm it actually works

Verify the connection

Run this from Setup → Apex → Execute Anonymous, or via the CLI, to confirm real GAM data comes back.

Anonymous Apex
GAMNetworkServiceClient.GAMConnectionResult result =
    GAMNetworkServiceClient.getCurrentNetwork();

System.debug(result);

A successful result looks like:

GAMConnectionResult:[
  currencyCode=USD,
  errorMessage=null,
  networkCode=<real network code>,
  networkDisplayName=<real network name>,
  success=true,
  timeZone=<network time zone>
]
8
If something goes wrong

Troubleshooting

Errors actually encountered while building and testing this, and what they mean.

Keystore file is corrupted

The file selected in Setup wasn't genuine JKS format — PKCS12 and other formats are rejected outright. Re-download from the wizard; don't substitute a manually-generated file.

AuthenticationError.NETWORK_CODE_REQUIRED

Expected if you call getCurrentNetwork() before a network code is known. Use discoverNetwork() instead for a brand-new connection — it uses getAllNetworks(), which doesn't require one.

invalid_grant: account not found (from Google)

The Salesforce side worked correctly and reached Google's token endpoint — this specific error means the service account itself isn't real/registered, or hasn't been added as a user inside the target GAM network yet. Add its email under GAM → Admin → Access & authorization → Users.

You have uncommitted work pending. Please commit or rollback before calling out

A callout was attempted in the same transaction as a preceding DML statement. This is a platform governor rule, not a bug — if you're scripting a test of your own, run assignPermissionSet() and discoverNetwork() as separate Apex executions, exactly as the LWC does.

Metadata deploy fails referencing gam_service_account_key

The certificate hasn't been imported yet (Phase 5), or was imported under a different name. The name must be exactly gam_service_account_key — this is what the wizard names it automatically, so this only happens if a certificate was imported manually outside the wizard flow.

Evidence, not assumption

What's been validated

Every claim in this document was verified against a live org before being written down. Summary of what was tested and how.

JKS keystore generationGAMJKSBuilder.cls

Generated a keystore from a throwaway RSA key using this Apex class, then validated it against real OpenJDK keytool: confirmed the certificate parses correctly, and round-tripped the private key to PKCS12 to confirm the recovered RSA modulus is byte-identical to the original key. This proves both the container format and the encryption algorithm are correct, not just superficially well-formed.

Metadata auto-provisioning on a genuinely blank orgGAMOnboardingProvisioningService.cls

Created a brand-new Salesforce Developer Edition org with none of this metadata present, ran the full wizard flow end to end (JKS generation → manual import → automatic deploy of External Credential, Named Credential, and Permission Set from nothing), and confirmed the deploy succeeded and the permission set assignment worked. This is the true first-time-client scenario, not a redeploy over already-working configuration.

Real GAM authenticationGAMNetworkServiceClient.cls

In the original working org, a real (already GAM-registered) service account successfully authenticated through this exact chain and returned live network data via discoverNetwork(). In the blank test org, a disposable/unregistered service account was used to confirm the request correctly reaches Google's real token endpoint and is evaluated there — it was rejected only because that specific test account wasn't GAM-registered, which is the expected, correct behavior on Google's side, not a defect in this automation.

Net result Every stage of the pipeline — keystore generation, metadata provisioning on a blank org, and real authentication against Google's servers — has been independently verified. Combined, they cover the full chain from a pasted JSON file to a live, working GAM connection.
